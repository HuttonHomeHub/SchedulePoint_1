over `apps/api/src`, `apps/web/src`, `packages/types/src` (591 lines, tests included); `marker` and `NONE` were
searched separately because both are dominated by unrelated meanings (axis markers, perf-probe markers, the
redactor's "type marker"; `SwimlaneSource.NONE`, the `'None'` display label). Each hit was then opened. Every
snapshot-level reader was found with `rg -n "SnapshotLevel|snapshot_level"`, every exhaustive switch with
`rg -n "case '(NOT_SNAPSHOTTED|NETWORK|ACTIVITY|NONE|FULL|…)'"`, and every writer of a column a tidy item narrows
was searched for by column name (commands quoted where a claim depends on them).

**The rule (spec §4.3), applied literally.** REMOVE a branch only if its **only** producer is a row written by an
older version. KEEP anything a fresh 1.1 database can still produce: plan never calculated, no active baseline,
side not scheduled, matched on code, removed work cross-plan, `swimlaneSource: NONE` (a request value), an
imported or API-created value. The engine (`apps/api/src/modules/schedule/engine/`) is not edited.

**Task key** (plan "Milestone M3"): **T1** boot re-derivation + history marker · **T2** baselines / revision
compare / EV API + their schema tidy · **T3** placement-migration route, export, module, staff diagnostics,
hierarchy legacy path, comments · **T4** web + `@repo/types` · **T5** test fixtures. §8 proposes moving some
items between T2/T3/T4; where it does, the row says so.

## 4. Q3 — can the #492 race leave activity dates on an unstamped plan? Traced: not by #492 itself; yes by a neighbour

**The #492 path is closed.** Recalculation (`schedule.service.ts:571-626`) takes the plan advisory lock
(`lockPlanForWrite` → `acquirePlanWriteLock`, `common/db/plan-advisory-lock.ts`), builds the graph from live
activities, then `writeResults` and `stampScheduleComputedAt` run in the **same transaction**. A plan/project/client
delete takes the same advisory key first (`lockPlansForCascade`, `hierarchy-lifecycle.service.ts:247-250`) and
soft-deletes the plan's activities in the same transaction as the plan. So: delete first → the recalculation sees
zero live activities, `writeResults` returns early (`schedule.repository.ts:830`) and nothing is dated; recalculation
first → the delete waits and the stamp lands. `writeResults` also filters `a.deleted_at IS NULL` and throws on a
short count (`:1060-1074`). The only writer of `early_finish` is `writeResults` (`rg -n early_finish apps/api/src` →
reads only elsewhere), and capture's precondition reads `early_finish` (`baselines.service.ts:577-585`).

**A neighbouring race is not closed.** A **project** delete resolves its plan list (`:513`), locks and cascades
only those plans, then soft-deletes plans by `projectId` (`:526`) — which also catches a plan committed into the
project after `:513` (limit (b) in `plan-advisory-lock.ts`). An import whose phase 1 commits a plan and its
activities in that window leaves a **soft-deleted plan with live activities, unlocked**; its phase-2
recalculation then dates the activities (`deleted_at IS NULL` on activities passes) while the stamp skips the plan
(`deleted_at IS NULL` on plans fails). Restoring the project's batch brings that plan back dated and unstamped, and
its first capture would then fail with 23502 under T8. (Client delete is safe for plans — `:501` uses
`id: { in: planIds }` — but has the same shape one level up at `:504`, `project.updateMany({ clientId })`.)

**Correction, 2026-11-09 (TECH_DEBT #576, closed).** The "neighbouring race" above does not exist, and this trace
missed why: the import commit takes the project row `FOR SHARE` for its whole transaction
(`interchange.service.ts`, `lockActiveProjectChainForShare`, #531), and a project delete takes it
`FOR NO KEY UPDATE` _before_ it reads its plan list (`lockProjectRowForDelete`), so the two serialise: an
import either commits first and is swept with its activities, or waits and is refused 404. The verdict below
(keep the columns nullable) was reached on the strength of this paragraph; the other cause it names, a plan
never recalculated, still holds, and NOT NULL remains an owner decision, not something this correction takes.

**Verdict:** keep the four baseline criticality columns nullable (T8 not taken); reword the sentinel comment to
name this cause. The race itself is a pre-existing integrity defect, not old data, and outside M3: **file it as a
`docs/TECH_DEBT.md` row** beside #492 (fix: delete by the locked id list, and decide what happens to a plan or
project created in the window). If that fix lands before 1.1.0, T8 can be reconsidered in the still-editable
baseline.
