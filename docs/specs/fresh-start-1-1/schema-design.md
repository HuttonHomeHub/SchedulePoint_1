# Fresh start 1.1 — database design

- **Author:** database-architect, 2026-11-08
- **Status:** Approved — by the product owner, 2026-11-08 (§12 records the answers). Design only: no migration, `schema.prisma` or code has been changed.
- **Scope:** the database half of the 1.1.0 release: the squashed baseline migration, the tidy folded
  into it, refusing a pre-1.1 database, the backup interaction, and how to prove the baseline is right.
  The feature spec and plan for the whole release are the feature-analyst's, in this folder.
- **Owner decisions this rests on (2026-11-08):** 1.1.0 needs a fresh, empty database, and everything
  in the old one is discarded test data. The ~85 migrations become one baseline. The image refuses a
  pre-1.1 database and never half-migrates it. Leftovers that existed only for rows saved by older
  versions are tidied inside the baseline.

Every claim below that decides something says what was run or read. "Measured" means it was run on a
scratch PostgreSQL **16.15** (production runs 17; nothing here depends on the difference), with the
whole migration chain at `HEAD` applied migration by migration (`psql -1 -v ON_ERROR_STOP=1`).
`git diff --stat api-v1.0.0 HEAD -- apps/api/prisma apps/api/docker-entrypoint.sh apps/api/backup` is
empty, so `HEAD`'s chain **is** the 1.0.0 chain.

## 0. Summary

1. **One baseline migration** builds the tidied schema from empty. It is generated by
   `prisma migrate diff --from-empty --to-schema-datamodel`, with a hand-written raw-SQL section
   appended (§2). Recommended name: `20261109000000_baseline_1_1`.
2. **The tidy** (§3) removes three one-off migration-record tables and the "captured before this
   existed" label from the five baseline snapshot levels. It makes eleven columns NOT NULL that were
   nullable only for old rows, and turns four one-way CHECKs into both-way ones. Nothing in the
   tidy changes a published `/api/v1` response shape **if** the no-break option is taken for each
   item, and each no-break option is listed. One decision is unavoidably the owner's: the public
   `GET …/plans/:planId/placement-migration` endpoint (§3, T2).
3. **A pre-1.1 database is refused before anything touches it** (§4). This is a new `preflight` step
   in the entrypoint, ahead of the backup `pre-migrate` step and `prisma migrate deploy`. The rule is
   derived rather than listed: the baseline is the first migration directory the image ships, and a
   database with any applied migration whose name sorts **before** it is from an older generation.
   The order of the steps matters. Without the guard, Prisma records a failed baseline in the old
   database's `_prisma_migrations`, and the backup step takes a fresh copy on every restart (§4.2).
4. **The backup script needs two changes** (§5). `restore` and `check` currently call a pre-1.1 copy
   "made by a newer version of SchedulePoint", which is the wrong way round. And `pre-migrate` must
   never see an old database.
5. **Six places in application code read `_prisma_migrations` by migration name** (§6). After the
   squash none of those names exists. All six fail safe, as dormant code or a correct fallback, but
   they are dead code the plan should remove.
6. **Equivalence is proven by comparing catalogues, not by text-diffing dumps** (§7). The SQL is
   given in full and was run. A plain text diff of `pg_dump --schema-only` cannot work, because the
   baseline's column order differs from the chain's. The intended differences are written as
   executable SQL applied to the old chain, so the allow-list is code and the comparison is exact
   equality. Run it once, as a milestone task. A permanent gate is optional (§7.4).
7. **An ADR is needed** (§11): ADR-0215. It amends ADR-0018, ADR-0190, ADR-0192, ADR-0194 and
   ADR-0107 D2, and retires the "captured before" half of ADR-0025's amendments (ADR-0071 M3,
   ADR-0125, ADR-0126, the placement, swimlane and code snapshots) and ADR-0214's null rule.

## 2. The baseline migration

### 2.1 Name and position

`apps/api/prisma/migrations/20261109000000_baseline_1_1/migration.sql`. The only requirements are:

- it is the **lexically first** directory (Prisma applies in name order, and §4's rule depends on it);
- every pre-1.1 name sorts before it, and every future migration sorts after it.

Any timestamp later than the last legacy name (`20261108120000_total_float_minutes`) and earlier than
the first 1.1.x migration meets both. A unit test should pin "the first directory is the baseline"
(§4.4).

### 2.2 How to build it

1. Apply the tidy to `schema.prisma` (§3) and delete the 84 legacy directories.
2. `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` gives the
   tables, enums, Prisma-declared indexes and the FKs.
3. Append a **hand-written section** in this order:
   1. `CREATE EXTENSION IF NOT EXISTS "btree_gist";`. This goes **before** the generated part in
      practice, because the EXCLUDE constraints need it. Put it at the top of the file.
   2. The CHECKs, partial indexes, `NULLS NOT DISTINCT` uniques and EXCLUDE constraints, **grouped by
      table**, each with a one-line _why_ and its provenance as
      `-- was: <legacy migration> (git tag api-v1.0.0)`. Measurements recorded in old migration
      comments (the library search, recycle-bin, `idx_activities_parent_id_fk` and
      baseline-assignment index decisions) are cited by that provenance, not copied. DATABASE.md's
      "measure before adding an index, record the measurement in the migration comment" is then
      satisfied by reference, and the evidence stays reachable through the tag.
   3. `audit_events_reject_mutation()`, both triggers, and **both**
      `ALTER TABLE "audit_events" ENABLE ALWAYS TRIGGER …` statements, verbatim from
      `20260803170000_audit_events`.
4. Rules for the hand-written section:
   - Plain `CHECK`, never `NOT VALID`. On empty tables validation is free, and the chain has none
     left unvalidated (§1).
   - No `CONCURRENTLY`. Prisma runs the file in one transaction. ADR-0107 D1 established on a real
     database that a failed migration leaves the schema clean (P3018), so the baseline is atomic.
   - No `INSERT`. Nothing in the chain leaves a row behind (§1).
   - No `ALTER TYPE … ADD VALUE`. Every enum is created whole.
5. Prove it with §7 before it is committed. A migration is checksummed when it lands.

### 2.3 What the squash does to documentation inside the schema

- `schema.prisma` names **9 distinct legacy migrations in 16 places**
  (`grep -oE "2026[0-9]{10}_[a-z0-9_]+" schema.prisma`). Each becomes "the baseline" or
  "`<name>` at api-v1.0.0", depending on whether it points at _where the SQL is_ or _why it was decided_.
- `docs/DATABASE.md` (24 references) and `docs/DEPLOYMENT.md` (14) need the same pass. DEPLOYMENT.md's
  per-migration rollback and compensating-reverse instructions (lines ~800–1000, for example "the
  marker row is never deleted outside a rollback") describe migrations that no longer exist and can
  be removed.
- Long docblocks whose only subject is the old population (the "NONE IS PERMANENT …" passages) shrink
  with T3/T4 below. That is the bulk of the comment change, and it belongs in the same PR as the
  baseline.

## 4. Refusing a pre-1.1 database

### 4.1 The states, and the rule

Let **B** be the lexically first directory in `/app/prisma/migrations` (the baseline). A database is
classified, read-only:

| State       | Test                                                                     | Action                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fresh`     | No `_prisma_migrations`, and no table in `public`                        | Continue (Prisma creates everything).                                                                                                                                                         |
| `fresh`     | `_prisma_migrations` exists with **0 rows**                              | Continue. This is what `pre-migrate` already calls fresh (`schedulepoint-backup.sh:743–747`).                                                                                                 |
| `unmanaged` | No `_prisma_migrations`, but `public` has tables                         | **Refuse.** Prisma would refuse too (P3005), with a message an operator cannot act on.                                                                                                        |
| `current`   | No row named `< B`; a row named `B` that is finished and not rolled back | Continue.                                                                                                                                                                                     |
| `pre-1.1`   | Any row named `< B`, and no finished row `B`                             | **Refuse**, and point at the upgrade guide.                                                                                                                                                   |
| `mixed`     | Rows named `< B` that are unfinished **and** a finished row `B`          | **Refuse.** A 1.0 image was started against this 1.1 database (§4.3). Print the exact remedy (`prisma migrate resolve --rolled-back <name>` for each listed row). Never repair automatically. |
| `unknown`   | Rows exist, none `< B`, and no finished row `B`                          | **Refuse** (fail closed).                                                                                                                                                                     |

**Why "sorts before B" rather than a frozen list of 84 names.** It needs no constant in the image or
the script. It reads the same folder `prisma migrate deploy` and `pre-migrate` already read. And it
still works the day a second squash happens: the new baseline is first, and everything older is a
previous generation. The cost is a convention, "a migration's timestamp is later than the baseline's",
which Prisma's own ordering already demands. §4.4 pins it with a test. A manifest file
(`prisma/pre-1.1-migrations.txt`) is the alternative if the reviewer prefers explicit over derived.

Measured: the classification SQL (below) returns `fresh` on an empty database and `unknown-unmanaged`
on a chain-built database without Prisma's table. With a `_prisma_migrations` holding the 84 legacy
names it counts `older = 84, has_baseline = 0`.

```sql
SELECT CASE WHEN to_regclass('public._prisma_migrations') IS NULL THEN
         CASE WHEN EXISTS (SELECT 1 FROM pg_class WHERE relnamespace = 'public'::regnamespace AND relkind = 'r')
              THEN 'unmanaged' ELSE 'fresh' END
       ELSE 'managed' END;
-- when 'managed':
SELECT count(*) FILTER (WHERE migration_name < :'baseline')                                                    AS older,
       count(*) FILTER (WHERE migration_name = :'baseline' AND finished_at IS NOT NULL AND rolled_back_at IS NULL) AS has_baseline,
       count(*) FILTER (WHERE migration_name < :'baseline' AND finished_at IS NULL AND rolled_back_at IS NULL)     AS older_unfinished,
       count(*)                                                                                                  AS total
  FROM _prisma_migrations;
```

Compare names in the `C` collation (`migration_name COLLATE "C" < …`) so the result does not depend on
the database's locale. Prisma's own ordering is bytewise.

### 4.2 Where it runs, and why the order is load-bearing

`apps/api/docker-entrypoint.sh` today, under `set -e`: (1) `schedulepoint-backup.sh pre-migrate`,
(2) `prisma migrate deploy`, (3) `node dist/main.js`. The guard goes **first**:

```sh
sh /app/backup/schedulepoint-backup.sh preflight   # new: refuses a pre-1.1 / unknown database
sh /app/backup/schedulepoint-backup.sh pre-migrate
node_modules/.bin/prisma migrate deploy
exec node dist/main.js
```

What happens if the guard is missing or comes later, read from the code:

- **After `pre-migrate`:** against a pre-1.1 database, `pending = known − applied` = `{B}`, which is
  non-empty, so `pre-migrate` takes a copy (`schedulepoint-backup.sh:754–761`). Then something exits
  non-zero, Docker restarts the container (`restart: unless-stopped`, `docker-compose.release.yml:90`),
  and `pre-migrate` takes **another copy on every restart**. `pre-migrate` "never prunes" (script
  header, line 23). The result is a disk-filling loop on exactly the host whose operator is
  mid-upgrade.
- **No guard at all:** `prisma migrate deploy` does not refuse a history containing migrations it
  does not ship. Prisma's documentation says `migrate deploy` does not warn about applied
  migrations missing locally. That was **not reproduced here** because the Prisma CLI is not
  installed in this checkout; reproducing it is a milestone task. Deploy then runs B, whose first
  `CREATE TYPE` collides. Per ADR-0107 D1 (verified on a real database), that leaves the schema clean,
  records the failure in `_prisma_migrations` (P3018), and every retry reports P3009. So the old
  database is not half-migrated, **but it is written to**. It now holds a failed row named B, and a
  later attempt to start 1.0 against it also stops at P3009. The brief's "never half-migrate" is met
  by Prisma's transactionality. "Never touch it" is met only by the guard.

**Implementation choice.** Make it a new `preflight` command in `schedulepoint-backup.sh`, not a
separate Node CLI:

- the script already parses `DATABASE_URL` safely into `PG*` variables (header, "CONNECTION");
- it already has `known_migrations()` and the fail-closed, JSON-event style;
- it already runs first in the entrypoint;
- `scripts/backup-restore-check.sh` already drives it in CI;
- and §5's `verify_loaded` needs **the same classification**, so one function serves both.

Unlike `pre-migrate`, `preflight` must **not** skip when `/backups` is absent. The guard is
unconditional. The alternative is a Node CLI under `dist/cli/`, with a pure `classify()` that is
easier to unit test, at the cost of the rule living in two languages.

`preflight` should **also** be called at the top of `cmd_pre_migrate`, as belt and braces: removing
the entrypoint line must not silently restore the copy loop.

**On refusal:**

- exit 1 with one plain message;
- emit `{"event":"database.preflight_refused","state":"pre-1.1",…}`;
- if `/backups` exists, also write `UPDATE-HELD.txt` (the §4.12 precedent);
- read-only, at one query per restart, so the restart loop is harmless;
- the healthcheck never passes, so `web` (which waits for `api` to be healthy) does not start.

Suggested text, for the feature-analyst to own:

> DATABASE FROM AN EARLIER VERSION — SchedulePoint 1.1 starts with a new, empty database and has not
> changed this one. This database was made by SchedulePoint 1.0 or earlier. Nothing has been
> changed. To carry on, keep a backup of this database, then point SchedulePoint at a new, empty
> database: see docs/guides/<upgrade guide>. To go back to 1.0 instead, set API_IMAGE_TAG=1.0.0.

Concurrent replicas: each runs a read-only query, then `migrate deploy` takes its own advisory lock as
today. Nothing new to serialise.

### 4.3 The reverse direction: a 1.0 image against a 1.1 database

1.0 images are released and cannot be changed, so this is documentation, not design. Read from the
1.0 entrypoint and script:

1. 1.0's `pre-migrate` sees 84 shipped names pending, so it **takes a copy on every restart**.
2. Its `migrate deploy` applies `20260709142606_add_identity_tables`, which fails on `CREATE TABLE
"users"`, so P3018 and then P3009 for ever, with a failed legacy-named row left in the 1.1
   database's `_prisma_migrations`.

That row is §4.1's `mixed` state. The 1.1 `preflight` names it and prints the
`prisma migrate resolve --rolled-back` remedy.

The consequence is that ADR-0190's "Rollback is pinning `API_IMAGE_TAG` … to the previous versions"
**does not hold across 1.1**. The only way back to 1.0 is a 1.0 stack on the operator's kept backup,
restored into an empty database with a 1.0 image (§5). The upgrade guide must say so prominently, and
ADR-0215 amends ADR-0190 accordingly.

### 4.4 Tests the guard needs (ADR-0110: verified against the defect it names)

- **Unit**, for the shell function through `backup-restore-check.sh`'s harness: one database per state
  in §4.1 (fresh/no table, fresh/empty table, unmanaged, current, pre-1.1, mixed, unknown), asserting

  - no `starting API`;

  **The defect check:** with the `preflight` line deleted from the entrypoint, this step must fail

- `scripts/e2e-local.sh` reuses a persistent `app_test` database (`prisma migrate deploy` at line

## 7. Proving the baseline is right

### 7.1 Why not a text diff of `pg_dump --schema-only`

The chain adds columns over time, so `pg_attribute.attnum` order in the old database is historical.
The baseline generated from `schema.prisma` declares columns in field order. `pg_dump` prints
`CREATE TABLE` in `attnum` order, so a text diff would differ on nearly every table, and an allow-list
of diff lines would be long, brittle and unreviewable. Column order has no behavioural effect here:
Prisma names columns, and `pg_dump`'s COPY lists them.

### 7.2 The method

1. **old** := an empty database with the api-v1.0.0 chain applied
   (`git archive api-v1.0.0 apps/api/prisma/migrations`).
2. **expected** := old + `tidy.sql`, an executable statement of every intended difference (the §3
   choices). **The allow-list is code**, reviewed with the PR.
3. **new** := an empty database with the baseline applied by `prisma migrate deploy`.
4. Run the catalogue query below on **expected** and **new**. The outputs must be **identical**.
5. Also run `prisma:check-drift` on **new** (as CI already does). That covers Prisma's half, and step 4
   covers everything Prisma cannot see.

The catalogue query (column-order-insensitive, whitespace-normalised, extension-owned functions
excluded). It was run on the chain, and its counts match §1 (658 columns, 246 constraints, 191
indexes, 31 enums, 2 triggers, 1 function, 1 extension, 43 tables):

```sql
SELECT line FROM (
  SELECT 'ext '||extname AS line FROM pg_extension WHERE extname <> 'plpgsql'
  UNION ALL
  SELECT 'enum '||t.typname||' '||string_agg(e.enumlabel, ',' ORDER BY e.enumsortorder)
    FROM pg_type t JOIN pg_enum e ON e.enumtypid = t.oid
   WHERE t.typnamespace = 'public'::regnamespace GROUP BY t.typname
  UNION ALL
  SELECT 'col '||c.relname||'.'||a.attname||' '||format_type(a.atttypid, a.atttypmod)
         ||CASE WHEN a.attnotnull THEN ' NOT NULL' ELSE ' NULL' END
         ||COALESCE(' DEFAULT '||pg_get_expr(d.adbin, d.adrelid), '')
         ||CASE WHEN a.attgenerated <> '' THEN ' GENERATED '||a.attgenerated::text ELSE '' END
    FROM pg_attribute a JOIN pg_class c ON c.oid = a.attrelid
    LEFT JOIN pg_attrdef d ON d.adrelid = a.attrelid AND d.adnum = a.attnum
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind = 'r'
     AND a.attnum > 0 AND NOT a.attisdropped AND c.relname <> '_prisma_migrations'
  UNION ALL
  SELECT 'con '||conrelid::regclass::text||' '||conname||' '||regexp_replace(pg_get_constraintdef(oid), '\s+', ' ', 'g')
         ||CASE WHEN NOT convalidated THEN ' [NOT VALIDATED]' ELSE '' END
    FROM pg_constraint
   WHERE connamespace = 'public'::regnamespace AND conrelid <> 0
     AND conrelid::regclass::text <> '_prisma_migrations'
  UNION ALL
  SELECT 'idx '||indexname||' '||regexp_replace(indexdef, '^CREATE ', '')
    FROM pg_indexes WHERE schemaname = 'public' AND tablename <> '_prisma_migrations'
  UNION ALL
  SELECT 'trg '||pg_get_triggerdef(t.oid)||' enabled='||t.tgenabled::text
    FROM pg_trigger t JOIN pg_class c ON c.oid = t.tgrelid
   WHERE c.relnamespace = 'public'::regnamespace AND NOT t.tgisinternal
  UNION ALL
  SELECT 'fn '||md5(pg_get_functiondef(p.oid))||' '||p.proname
    FROM pg_proc p
   WHERE p.pronamespace = 'public'::regnamespace
     AND NOT EXISTS (SELECT 1 FROM pg_depend dp WHERE dp.objid = p.oid AND dp.deptype = 'e')
  UNION ALL
  SELECT 'tbl '||relname||' persistence='||relpersistence::text||' rls='||relrowsecurity::text
    FROM pg_class WHERE relnamespace = 'public'::regnamespace AND relkind IN ('r','v','m','S','p')
     AND relname <> '_prisma_migrations'
) s ORDER BY line;
```

### 7.3 What was demonstrated

- **Round trip:** chain → `pg_dump --schema-only --no-owner --no-privileges` → loaded into an empty
  database → catalogue identical (`diff` empty).
- **It catches the defects that matter.** In a copy, these three changes were each reported as a
  one-line diff:
  - `ENABLE` (origin) instead of `ENABLE ALWAYS` on `trg_audit_events_append_only` (`enabled=A` →
    `enabled=O`);
  - dropping `ck_baselines_swimlane_snapshot_shape`;
  - recreating `uq_code_swimlane_lanes_basis` without `NULLS NOT DISTINCT`.
- **The tidy is executable:** a prototype `tidy.sql` covering T1–T7 (T2 as P-b or P-c) applied
  cleanly to a copy of the chain in one transaction, leaving 40 tables and a 104-line catalogue
  difference. The enum shrink in Postgres is rename old type → create new → `ALTER COLUMN … TYPE …
USING col::text::new` → drop old. The two CHECKs that name enum literals must be dropped first and
  re-added. In the baseline itself the enum is simply created with one label.
- **Not demonstrated:** the Prisma-generated half, because the Prisma CLI is not installed in this
  checkout. That is the milestone's first run.

### 7.4 One-off or permanent?

- **One-off, mandatory**, as a milestone task. Write it as `scripts/check-baseline-equivalence.sh`
  (takes the tag and `tidy.sql`), run it locally and once in the squash PR's CI, and record the output
  in the milestone record. After the PR merges, the baseline is checksummed and immutable, and "old
  chain" means a tag, so repeating the comparison forever buys almost nothing.
- **Optional permanent follow-up** (an ADR-0105 "shared gate" trigger, so it needs its own approval):
  commit the catalogue output as `apps/api/prisma/catalog.snapshot.txt`, and have CI fail when the
  migrated database's catalogue differs from it. That would protect, release after release, exactly
  the objects `prisma:check-drift` cannot see: a later migration that drops a CHECK, recreates an index
  without its `WHERE`, or touches the audit triggers. The cost is one regenerated file per schema PR.
  **Recommended**, separately from 1.1.

## 8. ADR-0107 after the squash

ADR-0107's subject is "what to do when the failure mode is a property of the data, and every automatic
gate runs against data that cannot exhibit it."

- **For the baseline itself it does not apply.** The baseline only ever runs on an empty database (the
  guard enforces it), which is exactly what CI runs it on. It is the one migration where pristine CI is
  representative.
- **The tests that embodied it go with the migrations.** These replay a legacy `migration.sql` by path
  and are deleted: `account-issuer-migration`, `strip-drag-constraints-migration`,
  `strip-bars-do-not-move`, `finish-milestone-date-migration`, `cross-plan-lag-migration`,
  `drop-scheduling-mode-migration` (`apps/api/test/*.e2e-spec.ts`, each reads
  `prisma/migrations/<name>/migration.sql`). The schema tests that inspect the tables T1/T2 drop also
  shrink: `placement-schema`, `placement-migration-report`, plus the `clear-plan-tree` and
  `organization-export` cases for the record tables.
- **It matters more from the first post-1.1 migration on.** 1.1 is the first public release, so the
  first 1.1.x migration lands on real customer data, which CI has never seen. ADR-0107 stays Accepted
  and unchanged in principle; only D2's specific default is retired (T7). The plan should keep the
  populated-database test pattern available (the backup fixture is the closest standing harness) rather
  than lose it with the six files above.

**Answered 2026-11-08 by the product owner:** Q1 → **P-c** (remove the endpoint; the ADR-0190 break is taken
as a recorded one-time exception, see Q5). Q2 → **narrow** the level enums to what is produced. Q3 → the
recommended default: take the NOT NULL only once the #492 race is traced. Q4 → the recommended default:
load-and-count with a "restorable only by 1.0" note. Q5 → **1.1.0**, with ADR-0215 recording why it is not a
major. Q6 → a permanent catalogue gate is a separate follow-up, not this epic.

The questions as they were put:

- **Q1, the placement-migration endpoint (T2).** P-a: keep everything; zero risk; a table that is empty
  for ever. P-b (recommended): drop the table, keep `GET …/placement-migration` returning an empty
  report, and deprecate it for the next API major. P-c: remove the endpoint, which ADR-0190 D2 makes an
  API **major** and so incompatible with calling the release 1.1.0.
- **Q2, the level enums in the API (T3).** Keep `'NONE'` in `BaselineResponseDto`'s documented enum and
  `@repo/types`, never produced (recommended, no-break)? Or narrow them to `['FULL']`? Narrowing output
  breaks no client in practice, but it changes the documented OpenAPI.
- **Q3, the baseline criticality NOT NULL (T8).** Take it only once the #492 race is shown not to leave
  activity dates on an unstamped plan, or leave the sentinel nullable?
- **Q4, `check` of a pre-1.1 copy under 1.1 (§5).** Load-and-count it with a "restorable only by 1.0"
  note (recommended), or refuse it as `restore` does?
- **Q5, the version number (outside the database, raised because it bears on ADR-0190).** ADR-0190 D1
  promises "the operator's configuration surface", and D2 says a breaking change bumps the major. A
  release that refuses every existing database and cannot be rolled back by tag-pinning (§4.3) is
  arguably a break for an operator, even though every row is test data. Is **1.1.0** the intended
  number, with ADR-0215 recording why this is not a major (no external operator exists and the data is
  test data)? Or should it be **2.0.0**? This is the owner's call. The database design does not depend
  on it.
- **Q6, a permanent catalogue gate (§7.4).** Approve as a separate follow-up, or decline?

## M2-T1 equivalence proof (2026-11-09, database-architect)

**Scope.** M2-T1 ships the baseline as an **exact equivalent** of today's schema; the §3 tidy is folded
into the still-unreleased baseline in M3. So `expected` in §7.2 is the chain itself and the allow-list
(`tidy.sql`) is empty.

**What was built.** `apps/api/prisma/migrations/20261109000000_baseline_1_1/migration.sql`, 2,067 lines,
110,215 bytes, sha256 `84f2c9d9…92fa0b` (equal to the `_prisma_migrations.checksum` Prisma recorded for
it, which settles M2-T3's open question: Prisma's checksum is the SHA-256 of the file). Layout:
`btree_gist`; the output of `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma
--script` (Prisma 6.19.3) verbatim, except three marked hand edits adding `NULLS NOT DISTINCT`; 116

name; and the audit function and both triggers verbatim from `20260803170000_audit_events`.

**Differences from §2.2 found in practice.**

- The three `NULLS NOT DISTINCT` uniques are **declared** in `schema.prisma` as plain `@@unique`, so
  Prisma generates them and the clause is edited into the generated statement rather than added in
  the hand-written section (the first A-vs-generated comparison showed them as the only three
  objects the generated part had in a _different_ form; everything else it lacked was simply absent).
- No per-object "one-line why" was written. Text extracted from the old migrations' comments was
  unusable as one-liners (sampled: section banners, half sentences), and the constraint names are
  self-describing; the reason for each object is on its model in `schema.prisma` (one header note
  there now says legacy names in comments resolve at the tag) and in the cited migration.
- Postgres renders `CASE` CHECKs on one line; lines over 160 characters were broken before
  `WHEN`/`ELSE`/`END`. The comparison below is what proves the reformatting changed nothing.

**Command** (PostgreSQL 16.15, role `app`, both databases on the local server; `catalog.final.sql` is
